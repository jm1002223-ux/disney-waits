分析はデータの日数で段階的に解禁され、12/7に14日分がそろった時点で全ての分析が回せます。各フェーズの最終日(月曜)に、品質の判定基準で次に進めるかを確認します。

## 品質の判定基準

各フェーズの終わりにこの表で判定し、下回ったら「下回ったら」の列のとおりにします。

| 指標 | 測り方 | 合格ライン | 下回ったら |
| --- | --- | --- | --- |
| データの充足率 | 営業時間の15分枠のうち、記録がある割合 | 90%以上 | 実行ログを確認。大きな欠けの日は分析から外す |
| 待ち時間予測の誤差 | `--backtest` の平均誤差(混雑指数が分かっている場合、人気アトラクション) | ±10分以内 | 時間帯の形を平日/週末で分ける、外れ値の日を外す |
| 混雑指数の見込み精度 | 同上の「曜日の平均で仮定」と「指数なし」の差 | 指数なしより小さい | 旅行当日の指数は混雑カレンダーから決める |
| クラスタの分かれ方 | シルエット係数 | 0.25以上 | 特徴量を減らす、グループ数を指定し直す |
| クラスタの安定性 | ブートストラップの調整ランド指数(ARI) | 0.75以上 | データが増えるまで参考扱いにする |
| プランの余裕 | 最終プランの最後の予定と退園時刻の差 | 30分以上 | 省略候補の上から外す |

## データの前提と注意点

この期間は丸ごとホリデー期間で、普段の年より混み方の幅が大きくなります。特殊な日は分析で分けて扱います。

- **感謝祭の週(11/26〜11/29)**:年間でも指折りの繁忙日です。混雑指数の基準(100)が引き上がるので、この4日を含む場合と除く場合を比べます
- **クリスマス前(12/19〜12/26)**:学校が休みに入り、混雑が一段上がるのが例年の傾向です。旅行日がこの周辺なら、この期間のデータを重めに使います
- **12/24・12/25**:営業時間やショーが特別になることがあるので、`calendar_extra.csv` に公式の営業時間を入れておきます
- **表示待ち時間**:実際に並ぶ時間より長めに出ることが多いです。比較や順番には使えますが、絶対の分数は余裕を持って読みます
- **ライトニングレーン**:戻り時刻は取得できないので、プランでは見込み値(`ll_delay_*`)を使います
- **処理人数**:公表値がない推定値です。ゲスト占有率は傾向を見る目安として使います
- **シス調**:5分おきの記録なので、5分未満の停止や、GitHubの実行が遅れた時間帯の短い停止は数え落とします

## 毎週の作業

毎週月曜に30〜60分、次の順に進めます(現地の土日分まで入った状態で分析できます)。

- [ ] `git pull` して `python warehouse.py` を実行

- [ ] 気づいたことと、プランに反映することをClaudeに共有して、次の週の分析を決める

## リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| データ元(Queue-Times)が止まる・仕様が変わる | その期間のデータが欠ける | 毎朝の確認で早めに気づく。欠けた日は分析から外す |
| GitHubの定期実行が遅れる・止まる | 記録が粗くなる | 分析は15分単位なので多少の遅れは影響なし。止まったら手動実行で確認 |
| 33日分では季節や曜日の傾向が十分に取れない | 予測が不安定になる | 品質基準で判定し、不合格ならプランは中央値(混雑指数なし)で計算する |
| 感謝祭・クリスマスの特殊な日が平均をゆがめる | 普通の日の予測がずれる | 特殊な日を含める/除くの2通りで比べる |
| アトラクションの休止・名前の変更 | 対応表(`rides.json`)にないものが分析から漏れる | 月曜の作業で、対応表にないアトラクションが記録に出ていないか見る |
| 旅行当日の混雑指数を外す | 予測の精度が大きく落ちる | 混雑カレンダーと、過去の同じ曜日・同じ時期の指数の両方で決める。当日は公式アプリで前後を入れ替える |
