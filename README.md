# ディズニーランド・リゾート 待ち時間ロガー & ルート最適化

GitHub Actions で5分おき(パークの営業時間帯だけ)に待ち時間を取得してCSVに貯め、そのデータから1日の最適な回り方を計算します。

Powered by [Queue-Times.com](https://queue-times.com/)(待ち時間データの提供元。表示が利用条件です)

## ファイル構成

| ファイル | 役割 |
|---|---|
| `.github/workflows/collect.yml` | 5分おき(現地7時〜24時ごろ)に `collect.py` を動かし、データをコミットする |
| `collect.py` | 待ち時間を取得して `data/DL/日付.csv`・`data/DCA/日付.csv` に追記(現地時間で日付を分ける) |
| `analyze.py` | 貯めたデータから、アトラクションごと・15分ごとの待ち時間(中央値)を集計 |
| `model.py` | 混雑指数を計算し、指数ごとの待ち時間と列の人数(推定)を出す。グラフ付きレポートも作る |
| `insights.py` | アトラクションのグループ分け、朝いちばんに乗る価値のランキング、システム調整の確率と時間帯 |
| `warehouse.py` | CSVを分析用のデータベース(DuckDB+Parquet)にまとめる |
| `analysis.ipynb` | SQLで自由に切り口を変えられる分析ノート(Jupyter) |
| `calendar_extra.csv` / `shows.csv` | 日付ごとのイベント・天気・営業時間のメモ / ショーの時刻(自分で書き足す) |
| `gbm.py` | 勾配ブースティングで待ち時間を予測し、ほかの予測方法と精度を比べる |
| `plan.py` | 集計結果を使って、待ち+徒歩が最短になる回り方を計算 |
| `plan_DL.json` / `plan_DCA.json` | プランの条件(入退園時刻、乗りたいもの、パス、ショー、食事、優先度) |
| `rides.json` | アトラクションの番号(パークマップと同じ)・名前・おおよその座標・パス対象かどうか |

## 1. データ集めを始める(最初に1回だけ)

1. GitHubで新しいリポジトリを作る。**Public(公開)にしてください**
   - 公開リポジトリならActionsは無料で回し放題です。集めるのは公開されている待ち時間だけなので、公開して困る情報は入りません
   - 非公開だと無料枠が月2000分で、5分おきだと大きく超えます(非公開にするなら `collect.yml` の `*/5` を `*/30` に)
2. このフォルダの中身を全部アップロードする(`.github` フォルダも忘れずに)
3. リポジトリの **Settings → Actions → General → Workflow permissions** を **Read and write permissions** にして保存する
4. **Actions** タブ → `collect-wait-times` → **Run workflow** で1回手動実行して、`data/` にCSVができるか確認する

あとは放っておけば、パークの営業中は5分おきにデータが増えていきます(閉園中は書き込みません)。3月にサマータイムが始まると取得時間帯が1時間ずれますが、分析には影響しません。GitHubが混んでいると実行が数分〜十数分遅れることがありますが、問題ありません。

## 2. プランを計算する

パソコンにPython 3.9以上が入っていればOK。追加のライブラリは不要です(Windowsだけ `pip install tzdata` が必要)。

```bash
git pull                                   # 貯まったデータを手元に持ってくる
python analyze.py --park DL                # 集計 → profiles/DL.json, profiles/DL_best.csv
python plan.py plan_DL.json                # 計算 → plan_DL.md
```

`plan.py` のオプション:`--fast`(反復を1/10にして試す。結果は粗い)、`--robust`(戻り時刻の見込みが0.5倍・1.5倍にずれても、取るパスが変わらないか確かめる)、`--no-compare`(「マルチパスなし」との比較を省く)。

マルチパスは、**優先順位の高いものから順に**、入園時刻から予約していく前提で計算します。次の予約は「使った後」か「予約から2時間後」の早い方です。スタンバイでも空いているもの(`ll_min_standby` 未満)と、戻り時刻が `ll_use_until` に入らないものはパスを取りません。`plan_DL.md` には、パスの取り方の表(予約する時刻・戻り時刻・乗る時刻・取らない理由)と、マルチパスを使わない場合との比較が出ます。

- `profiles/DL_best.csv` はExcelで開けます。アトラクションごとの「空いている時間帯」「混む時間帯」の一覧です
- 計算は約3分かかります(焼きなまし法で何十万通りも試すため。「マルチパスなし」との比較を含む。`--robust` を付けると約5分)
- 平日だけ・週末だけで集計したいときは `--days weekday` / `--days weekend`、期間を絞るときは `--from 2026-12-01 --to 2026-12-20`

## 2.5 混雑指数モデル(`model.py`)

```bash
python model.py --park DL                  # → models/ に一式
```

貯めたデータから次の3つを作ります。結果は `models/DL_report.html` をブラウザで開くとグラフで見られます。

1. **混雑指数**:人気アトラクションの待ち時間が、データ期間の平均の何%か。100 = 平均的な日、120 = 2割混んでいる日(`models/DL_daily.csv`)
2. **アトラクションごとの反応**:混雑指数が80/100/120の日の平均待ちと、「指数が10上がると何分増えるか」(`models/DL_rides.csv`)。時間帯ごとの形(朝は平均の何倍、昼は何倍…)も覚えておき、「指数Xの日のY時の待ち時間」を予測します
3. **列に並んでいる人数の推定とゲスト占有率**:リトルの法則(列の人数 ≒ 1時間の処理人数 ÷ 60 × 待ち時間)で、時間帯ごとにどのアトラクションの列に何人いるか(`models/DL_queue.csv`)と、列に並ぶ人全体のうち何%がそのアトラクションにいるか(1日・2時間ごと、`models/DL_share.csv`)を出します

`plan_DL.json` の `"crowd_index"` に数字(例:`120`)を入れると、`plan.py` はこのモデルで「その混み具合の日」の待ち時間を予測してプランを作ります。`null` のままなら `analyze.py` の中央値を使います。

### 予測の精度を検証する

```bash
python model.py --park DL --backtest       # → models/DL_backtest.csv
```

貯めたデータから1日ずつ隠し、残りの日で作ったモデルで隠した日の待ち時間を予測して、実際との差(平均誤差、±何分)を測ります(5日分以上必要)。次の3通りを比べます。

| 予測のしかた | 意味 |
|---|---|
| 指数が分かっている場合 | その日の混雑指数を正しく当てられたときの精度(モデルの上限) |
| 指数を曜日の平均で仮定 | 混雑指数を「同じ平日/週末の平均」と見込んだときの精度(何も調べずに使った場合) |
| 指数なし | 混雑指数を使わず、過去の同じ時間帯の平均だけで予測したときの精度(比較の基準) |

「指数が分かっている場合」と他の2つの差が、**当日の混雑指数をどれだけうまく見込めるかで精度がどれだけ変わるか**を表します。旅行の日の `crowd_index` は、混雑カレンダー(Queue-Timesなど)を見て決めるのがおすすめです。

注意:
- 処理人数(`rides.json` の `capacity_per_hour`)は公表値ではなく推定の目安です。知っている値があれば直してください
- 表示される待ち時間は実際より長めのことが多いので、列の人数は「傾向を見るための目安」です
- 列にいない人(食事・買い物・移動中)は数えていないので、入園者数そのものではありません
- 混雑指数の意味は「このデータ期間の中で」の相対値です。データを足すと基準が変わります

## 2.6 分析(`insights.py`)

```bash
python insights.py --park DL               # → insights/ に一式(5日分以上必要)
```

`insights/DL_report.html` をブラウザで開くと見られます。

1. **グループ分け**:平均待ちの大きさ・時間帯ごとの形・朝の伸び・混雑への反応・日ごとのぶれ・止まりやすさで、似たアトラクションをk-meansで分類。グループ数はシルエット係数が最大になる数を自動で選びます
   - 精度の確認:日をランダムに選び直して50回分類し直し、同じ分け方になる度合い(調整ランド指数ARI)を出します。0.75以上なら安定、0.5未満ならデータ不足
   - アトラクションごとの「所属の確からしさ」も出すので、どのグループにも入りきらない境目のものが分かります
2. **朝いちばんに乗る価値**:開園直後に乗ると、昼(11〜17時)に乗るより何分得するか。開園時に止まっていることが多いものは割り引きます。全体の順位とグループ内の順位(`insights/DL_ropedrop.csv`)
3. **システム調整(シス調)**:営業中に「運営中」でなくなった記録から、1日に1回以上止まる確率、1日の回数、平均の停止時間、開園時に動いていない確率、止まりやすい時間帯(時間帯ごとの停止割合のヒートマップ)(`insights/DL_downtime.csv`)
   - 5分おきの記録なので、5分未満の停止は見逃すことがあります(実行が遅れた時間帯はもっと粗くなります)。終日運休の日(改修など)は数えません

## 2.7 データベースで自由に分析する(`warehouse.py` + `analysis.ipynb`)

何百万行になっても速く扱えるように、CSVを分析用のデータベースにまとめて、SQLで分析します。

```bash
pip install -r requirements.txt            # 最初の1回だけ(duckdb, pandas, matplotlib, jupyterlab)
git pull                                   # 最新のデータを取ってくる
python warehouse.py                        # → warehouse/(データが増えたら毎回実行し直す)
jupyter lab analysis.ipynb                 # ブラウザで分析ノートが開く
```

- **Parquet**:CSVを列ごとに圧縮した形式に変換し、パーク・月ごとに分けて保存します。サイズが小さく、読み込みが速くなります
- **DuckDB**:サーバー不要のSQLデータベースです。`warehouse/disney.duckdb` に次のテーブルが入ります

| テーブル/ビュー | 中身 |
|---|---|
| `fact_waits` | 待ち時間の記録(1行 = 1回の取得 × 1アトラクション、重複除去済み、現地時刻・15分枠付き) |
| `dim_ride` | アトラクションの属性(番号・名前・座標・処理人数・パス対象) |
| `dim_calendar` | 日付の属性(曜日・週末・アメリカの祝日・ホリデー期間・推定営業時間・混雑指数・`calendar_extra.csv` の内容) |
| `dim_show` | ショーの時刻(`shows.csv`。日付が `*` の行は毎日) |
| `v_slot_profile` | アトラクション × 15分ごとの待ち時間(中央値・平均・90%点・件数) |
| `v_daily_ride` | アトラクション × 日の平均・最大待ちと運営率 |
| `v_downtime_events` | 営業中に止まった区間(開始・再開・時間帯) |
| `v_queue_people` | 列の人数の推定とゲスト占有率 |

`analysis.ipynb` には、混雑指数の推移、アトラクション×時間帯のヒートマップ、平日と週末の比較、混雑指数への反応、ショー中に空くアトラクション、シス調、ゲスト占有率、一緒に混むアトラクション(相関)、朝いちばんの価値、の9つの分析と、自由にSQLを書くセルが入っています。どのセルもSQLを書き換えれば切り口を変えられます(先頭の `PARK = "DL"` を `"DCA"` にすればカリフォルニア・アドベンチャー)。

- `calendar_extra.csv` に、日付ごとのイベント・天気・公式の営業時間を書き足していくと、「雨の日だけ」「イベントの日だけ」のような分析ができます
- `shows.csv` は、当日のアプリで見たショーの時刻に合わせて直すと、ショー中の分析が正確になります
- `warehouse/` はPCの中で作り直すものなので、GitHubにはアップロードしません(`.gitignore` 済み)

## 2.8 勾配ブースティング(`gbm.py`)

```bash
python warehouse.py
python gbm.py --park DL                    # 1〜数分(--fast で軽く)
```

「条件で分ける小さな決定木」をたくさん作り、前の木の外れを次の木が直すことをくり返して予測する手法です(scikit-learn の HistGradientBoostingRegressor。LightGBMと同じ方式)。曜日・祝日・時間帯・開園からの経過時間・営業時間の長さ・天気・イベント・ショーの時間帯・混雑指数を条件として使います。

次の5つを、学習に使っていない日で採点して比べます(日ごとに分けた交差検証)。結果は `models/DL_gbm_compare.csv`。

| 予測 | 内容 | 使いどころ |
|---|---|---|
| A 過去の平均 | アトラクション×15分枠の平均 | 比べるための基準 |
| B 混雑指数モデル | `model.py` と同じ考え方 | 単純なモデルの代表 |
| C GBM(事前・指数あり) | 上の条件+その日の混雑指数 | 混雑指数を見込める場合の事前予測 |
| D GBM(事前・指数なし) | C から混雑指数を抜く | 何も調べずに前日までに予測する場合 |
| E GBM(当日・30分先) | D+30分前・60分前の待ち時間 | 当日に組み直す場合 |

`models/DL_gbm_importance.csv` には「どの条件が予測に効いているか」(その条件をでたらめに入れ替えると誤差が何分増えるか)が出ます。

`plan_DL.json` の `"wait_model"` を `"gbm"` にし、`"date"`(旅行日)、`"crowd_index"`(分かれば)、`"weather"`(`calendar_extra.csv` と同じ書き方)を入れると、`plan.py` は勾配ブースティングの予測でプランを作ります。`"median"` のままなら過去の中央値、`crowd_index` だけ入れると混雑指数モデルです。

## 3. 条件を変える(`plan_DL.json`)

| 項目 | 意味 |
|---|---|
| `entry` / `exit` | 入園・退園の時刻 |
| `wait_model` | 待ち時間の予測方法。`median`(過去の中央値)/ `gbm`(勾配ブースティング) |
| `date` / `weather` / `event` | 旅行日・天気・イベント(`gbm` のときに使う) |
| `crowd_index` | 想定する混雑指数(例:`120`)。`null` なら使わない |
| `multi_pass` / `standby` | 乗りたいもの(番号はパークマップの番号)。**どちらのリストに入れても扱いは同じ**で、パスを取るかどうかは下の `ll_*` で決まる(マルチパスの対象かどうかは `rides.json` で判断) |
| `single_pass` | シングルパスで乗るもの(ディズニーランドは19、カリフォルニア・アドベンチャーは11) |
| `priority` | 優先度(数字が大きいほど省かれにくく、パスも先に取る。指定しなければ3) |
| `use_multi_pass` | マルチパスを使うか(既定 `true`) |
| `ll_use_until` | パスで乗り終える時刻の上限(DLは `23:00`、DCAは閉園22時の1時間前の `21:00`)。戻り時刻がこれに入らないものは予約せず、次の候補に回す |
| `ll_buffer_min` | 戻り時刻のバッファ。見込みより何分遅れる前提で計算するか(既定15) |
| `ll_min_standby` | パスを取る基準。パスを使える時間帯のスタンバイ予測の平均がこれ(分)未満なら「スタンバイで十分」として取らない(既定30) |
| `ll_priority` | パスを取る順番を自分で決めるとき、番号を並べる(ここに入れたものは `ll_min_standby` で外さない)。空なら「優先度 → 人気 → スタンバイ平均が長い順」 |
| `ll_skip` | パスを取らないもの(スタンバイで乗る) |
| `ll_delay_override` | アトラクションごとに戻り時刻の見込みを変えるとき。例:`{"51": [90, 0.3]}` |
| `shows` | ショーの時刻と場所(`near` に近くのアトラクション番号)。**当日のアプリの時刻に合わせて直す** |
| `meals` | 食事をとる時間帯と所要時間 |
| `ll_delay_high` / `ll_delay_mid` | マルチパスの戻り時刻の見込み。人気のもの/それ以外で「取った時刻から何分後か」を `[基本の分, 入園からの経過分×係数]` で指定 |

## 計算の前提と限界

- 待ち時間は「その時刻の過去の中央値」です。当日の混雑・運休でずれるので、当日はアプリを見て前後を入れ替えてください
- データが少ないアトラクション(数日分しかない、など)は精度が低く、データがないものは推定値を使います(出力の「種類」欄に `実データ`/`推定` と表示)
- 徒歩時間はおおよその座標からの直線距離×1.35、分速70mで計算しています
- マルチパスの戻り時刻はAPIから取れないので、`ll_delay_*` の見込み値に `ll_buffer_min` を足して計算しています。当日アプリで実際に取れる時刻を見て、ずれが大きければ数字を直して再計算してください
- ホリデー期間はデータの傾向が普段と違います。旅行と同じ時期(12月)のデータが貯まってから計算するのがおすすめです

## ダッシュボード(`dashboard/`)

`music-lesson-portal` と同じ見た目(Next.js + Tailwind + Recharts)の画面で、集計結果を見られます。出すのは集計値だけで、生データの行は入れません。

| 画面の部品 | 中身 |
|---|---|
| 指標のタイル | 集計期間、データ充足率(合格ライン90%)、記録数、最後の取得時刻 |
| 時間帯ごとの待ち時間 | アトラクションを選ぶと、15分ごとの中央値(線)と90%点(帯)。全日・平日・週末を切り替えられる |
| 日別の混雑指数 | 期間平均を100とした棒グラフ |
| アトラクション × 時間帯 | 各時台の中央値のヒートマップ。行を押すと上のグラフが切り替わる |
| アトラクション一覧 | 平均、ピーク、空く時刻、稼働率、シス調の回数と分、最後の取得 |
| データ品質 | 日ごとの取得回数と充足率、実行間隔、`rides.json` にない名前 |

手元で見る(パスワードなし):

```bash
python warehouse.py
python export_dashboard.py        # → dashboard/data/DL.json, DCA.json
cd dashboard
npm install                        # 初回だけ
npm run dev                        # → http://localhost:3000
```

友人に見せる(Vercel、パスワード付き):

```bash
npm i -g vercel && vercel login    # 初回だけ
cd dashboard
vercel link                        # 初回だけ。新しいプロジェクトとして作る
vercel env add DASHBOARD_PASSWORD production   # 初回だけ。見せる相手に伝えるパスワード
vercel --prod                      # 集計を書き出した後、毎回これで更新
```

- 開くとユーザー名とパスワードを聞かれます。ユーザー名は何でもよく、パスワードだけを確かめます
- `dashboard/data/*.json` は git に入れません(`.gitignore`)。Vercel には CLI で手元から上げます。GitHub と連携すると、JSON なしでビルドされて空の画面になるので、連携しないでください
- 検索エンジンには載らない設定です(noindex)。URL とパスワードを渡すのは親しい人だけにしてください。もっと広く見せる場合は、事前に Queue-Times に相談します
